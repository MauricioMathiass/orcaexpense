================================================================================
 ORCAFY EXPENSE (OrcaEXPENSE) - DOCUMENTACAO COMPLETA DO CODIGO
================================================================================

Este arquivo explica, arquivo por arquivo e trecho por trecho, tudo o que foi
desenvolvido no projeto. Nos arquivos .jsx/.js (a logica da aplicacao) a
explicacao segue quase linha a linha. Nos arquivos .css a explicacao e feita
por bloco/regra (explicar "cada linha" de um valor tipo `padding: 24px` nao
agregaria informacao), descrevendo o que cada classe controla visualmente.

Stack: React 18 + Vite 5, JavaScript puro (sem TypeScript), sem backend -
todo o estado vive em memoria (useState), ou seja, ao recarregar a pagina os
dados voltam ao valor inicial definido no codigo.

Fluxo geral: main.jsx renderiza App.jsx, que renderiza DashboardLayout.jsx.
O DashboardLayout guarda TODO o estado da aplicacao (cartoes, despesas, modais
abertos, valores digitados nos formularios) e repassa esse estado + funcoes
de manipulacao via props para as 3 paginas (Overview/Cards/Expenses), que por
sua vez repassam para os componentes visuais (CardsPanel, ExpensesPanel,
CardChecklist, etc). Ou seja, e um fluxo unidirecional classico de React:
estado desce via props, eventos sobem via callbacks (funcoes passadas por
props que sao chamadas dentro dos componentes filhos).

--- FUNCOES DE DESPESAS FIXAS (linhas 67-106) ---

 67-88 function toggleExpense(id) { ... }
     -> chamada quando o usuario marca/desmarca uma despesa como paga
        (checkbox). Passos:
        1. Acha a despesa pelo id; se nao existir, sai.
        2. Calcula `nextPaid` (o oposto do estado atual `paid`).
        3. Atualiza a lista de despesas trocando `paid` daquele item.
        4. Ajusta `totalValue`: se acabou de ser marcada como PAGA, SUBTRAI
           o valor do total (a logica de negocio e "valor total de gastos"
           representa o que ainda falta pagar); se foi DESMARCADA, soma de
           volta.
        5. Se a despesa tiver `cardId` (ou seja, e uma "Fatura - X" ligada a
           um cartao), tambem atualiza o `spent` desse cartao: paga -> zera
           o gasto do cartao (`0`); despaga -> volta o gasto para o valor da
           fatura (`amount`).

 90-106 function deleteExpense(id) { ... }
     -> exclui uma despesa da lista. Se a despesa excluida estava PAGA,
        devolve o valor dela ao `totalValue` (pois deixa de estar "descontada"
        do total) e, se estava ligada a um cartao, restaura o `spent` do
        cartao para o valor da fatura.

--- FUNCOES DE CARTOES (linhas 108-142) ---

108-142 function handleAddCard(event) { ... }
     -> chamada ao submeter o formulario "Novo cartao".
        - `event.preventDefault()` evita o recarregamento de pagina padrao
          de formularios HTML.
        - Valida: marca/bandeira nao vazias e exatamente 4 digitos finais;
          se invalido, apenas retorna sem fazer nada (o botao Adicionar ja
          fica desabilitado nesses casos, entao isso e uma segunda camada de
          seguranca).
        - Converte limite/gasto digitados (string) para numero com `Number(...) || 0`.
        - Gera um `id` unico usando `Date.now()` (timestamp em ms).
        - Reaproveita o `holder` (nome do titular) do primeiro cartao
          existente, para manter o mesmo nome em todos os cartoes.
        - Adiciona o novo cartao ao `cardsState`.
        - Cria AUTOMATICAMENTE a despesa "Fatura - <MARCA>" ligada a esse
          cartao (mesmo padrao usado na inicializacao).
        - Limpa todos os campos do formulario e fecha o modal.

--- SINCRONIZACAO CARTAO <-> FATURA (linhas 144-151) ---

144-151 function syncCardBillAmount(cardId, delta) { ... }
     -> funcao central de sincronizacao: recebe o ID do cartao e um "delta"
        (diferenca a aplicar, pode ser positivo ou negativo). Se o delta for
        0/falsy, nao faz nada. Caso contrario, percorre as despesas e, na que
        tiver `cardId` igual, soma o delta ao `amount` dela. Isso garante que
        a despesa "Fatura - X" sempre reflita exatamente o gasto atual do
        cartao, sem precisar recalcular do zero - so aplica a diferenca.

--- CHECKLIST DE COMPRAS (linhas 153-272) ---

153-193 function handleAddChecklistItem(event) { ... }
     -> chamada ao submeter o formulario "Novo item" da lista de compras.
        - Bloqueia envio se o nome estiver vazio.
        - `cardId` vem do estado `addingChecklistItem` (setado quando o
          usuario clicou em "Adicionar" dentro de um cartao especifico).
        - Calcula `installments`: se for compra parcelada, usa
          `Math.max(2, Number(...) || 2)` (garante um minimo de 2 parcelas,
          mesmo se o campo estiver vazio ou invalido); senao, `undefined`.
        - Calcula `amount` (a IMPLEMENTACAO MAIS RECENTE, valor manual da
          parcela): se parcelado, `amount = installments * valorDaParcela`
          (o total da compra e DERIVADO multiplicando as parcelas pelo valor
          unitario digitado pelo usuario); se nao parcelado, e simplesmente o
          valor digitado no campo unico "Valor (R$)".
        - Atualiza `cardsState`: no cartao correspondente, soma `amount` ao
          `spent` (o gasto do cartao sobe imediatamente pelo valor TOTAL da
          compra, mesmo que ela seja parcelada - reflete o comportamento
          real de cartao de credito, onde o limite e comprometido no ato da
          compra) e acrescenta o novo item ao array `checklist` do cartao,
          com `id` unico (`item-<timestamp>`), `name`, `amount`,
          `installment` (booleano) e `installments` (numero ou undefined).
        - Chama `syncCardBillAmount(cardId, amount)` para a Fatura andar
          junto.
        - Reseta todos os campos do formulario e fecha o modal
          (`setAddingChecklistItem(null)`).

195-212 function deleteChecklistItem(cardId, itemId) { ... }
     -> localiza o item a ser removido (para saber o `amount` dele antes de
        apagar), remove do `checklist` do cartao, SUBTRAI esse valor do
        `spent` do cartao, e sincroniza a Fatura com um delta negativo
        (`-(target?.amount || 0)`).

214-225 function handleOpenEditChecklistItem(cardId, item) { ... }
     -> chamada ao clicar no lapis (editar) de um item do checklist. Preenche
        todos os campos do modal de edicao com os dados atuais do item:
        - nome, valor total (`amount`), se e parcelado, numero de parcelas.
        - PONTO IMPORTANTE (ultima feature implementada): como o campo
          exibido no formulario agora e o "valor da parcela" (nao mais o
          total), e o item so guarda o TOTAL (`amount`) + `installments`, essa
          funcao precisa RECONSTRUIR o valor da parcela dividindo:
          `item.amount / item.installments`. Assim, ao reabrir o item para
          editar, o campo "Valor da parcela" aparece corretamente preenchido
          com o valor unitario, e nao com o total.

227-272 function handleSaveChecklistItem(event) { ... }
     -> chamada ao submeter o formulario de EDICAO de um item.
        - Pega `cardId`/`itemId` do estado `editingChecklistItem`.
        - Recalcula `installments` e `amount` com a MESMA logica do "add"
          (installments * valor da parcela, se parcelado).
        - Busca o `amount` ANTERIOR do item (`previousAmount`) dentro do
          `cardsState` atual, para poder calcular `delta = amount - previousAmount`
          (a diferenca entre o novo valor e o valor antigo).
        - Aplica esse `delta` ao `spent` do cartao (soma, podendo ser
          negativo se o novo valor for menor que o antigo) e atualiza o item
          dentro do array `checklist` com os novos dados.
        - Sincroniza a Fatura com o mesmo `delta`.
        - Fecha o modal e limpa todos os campos de rascunho.

 RESUMO DAS REGRAS DE NEGOCIO MAIS IMPORTANTES
================================================================================
1. `card.spent` (gasto atual) SOBE imediatamente pelo VALOR TOTAL de uma
   compra assim que ela e adicionada ao checklist, mesmo que seja parcelada
   - isso reflete o comportamento real de um cartao de credito (o limite e
   comprometido no ato da compra, mesmo a fatura chegando parcelada).
2. `installments` (numero de parcelas) e apenas METADADO de exibicao - usado
   so para mostrar "10X - R$150/mes" na lista, nunca influencia o total
   somado ao limite.
3. O usuario digita o VALOR DA PARCELA manualmente (feature mais recente); o
   TOTAL da compra e sempre DERIVADO (`parcelas x valor_da_parcela`), tanto
   ao criar quanto ao editar um item.
4. Toda alteracao no checklist de um cartao (adicionar/editar/excluir item)
   passa por `syncCardBillAmount`, que mantem a despesa "Fatura - <cartao>"
   sempre igual ao `spent` real do cartao, aplicando a diferenca (delta) em
   vez de recalcular tudo do zero.
5. "Limite Disponivel" (numero grande exibido no cabecalho de Meus Cartoes)
   = soma de todos os limites - soma de todos os gastos; DIMINUI a cada novo
   gasto (comportamento pedido explicitamente pelo usuario, em vez de
   mostrar um limite total fixo).
6. Estado de selecao de cartao usa sempre um ID (nunca o objeto inteiro) para
   garantir que a interface reflita o estado mais recente apos qualquer
   atualizacao.
